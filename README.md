# ReceiptToExcel · 영수증 장부

영수증 사진을 PC에서 업로드하고, 추출된 내용을 확인·수정한 뒤 경비 지출장부로 내보내는 **1인용 로컬 Spring Boot 프로그램**입니다. AWS, Docker, 별도 DB 서버, 유료 AI API가 필요하지 않습니다. 실행 중에만 PC 안의 내장 웹 서버가 동작하고 `127.0.0.1`에서만 접속을 받습니다.

## 빠른 실행

**고객용 실행:** 릴리스의 `ReceiptToExcel-0.3.0-windows-x64.zip`을 모두 압축 해제하고 **ReceiptToExcel.exe**를 실행합니다. Java·IntelliJ·Maven 설치와 JAVA_HOME 설정 없이 동봉된 실행 환경으로 동작합니다. 준비 후 브라우저가 자동으로 열리며 종료는 관리 창에서 합니다. [Windows 실행·배포 안내](docs/RELEASE.md)

초록색 **Code → Download ZIP**은 개발용 소스이므로 아래 개발 환경이 필요합니다. 고객에게는 위 실행용 릴리스 ZIP을 전달하세요. 개발자는 `build-release.ps1`로 실행용 ZIP을 생성할 수 있습니다.

**IntelliJ IDEA**에서 이 폴더를 Open → Maven 프로젝트로 가져옵니다.

1. Project SDK와 Maven Runner JRE를 **Java 17 이상**으로 선택합니다. 현재 PC의 Java 17로 검증했습니다.
2. Maven 의존성 다운로드가 끝나면 `src/main/java/kr/local/receipts/ReceiptApplication.java`의 ▶ 버튼을 누릅니다.
3. Run Configuration의 Working directory는 **프로젝트 최상위 폴더**로 지정합니다. `pom.xml`과 `data`가 있는 위치입니다.
4. 브라우저에서 **http://127.0.0.1:8080** 을 엽니다.

IntelliJ 없이도 `start-local.cmd`를 더블 클릭하거나 다음 명령으로 실행할 수 있습니다.

```powershell
cd C:\Users\Chung_Seungho\Documents\ReciptToExcel
.\mvnw.cmd spring-boot:run
```

처음 빌드할 때 Maven과 라이브러리를 받으므로 인터넷이 필요합니다. 다운로드가 끝나면 기본 OCR·장부·XLSX 기능은 오프라인으로 사용할 수 있습니다. 실행 중인 터미널은 유지하세요. 종료는 IntelliJ의 ■ 또는 터미널의 Ctrl+C입니다. 이미 실행 중이면 같은 포트로 다시 시작하지 말고 열린 앱을 사용하세요.

Codex가 띄워 둔 미리보기는 `stop-preview.cmd`로 종료할 수 있습니다. 이후 IntelliJ에서 실행하세요. 이 파일은 기록된 미리보기 PID와 프로젝트 JAR 경로가 일치할 때만 종료합니다. 사용자가 IntelliJ 또는 `start-local.cmd`로 실행한 앱은 해당 창에서 종료하세요.

포트 8080이 사용 중이면 환경변수 `PORT=8081` 또는 `application-local.properties`의 `server.port=8081`로 바꿉니다.

## PDF 연속 스캔

한 페이지에 영수증 한 장인 PDF를 페이지별로 등록합니다. PDF는 25MB·최대 20쪽, JPG·PNG는 10MB를 지원합니다. 진행 페이지·중복 제외·실패 페이지를 표시하고 원본 PDF를 보관합니다. [PDF 사용 안내](docs/PDF.md)

## 실제 사용 순서

1. 선택적으로 **업무 목적**을 입력합니다. 예: `직원 점심 식사`, `거래처 식사`, `회의용 커피`. 목적을 먼저 입력하면 분류에 참고합니다.
2. 바탕화면 등에서 JPG/PNG 사진을 선택하거나 끌어 놓습니다. 여러 장도 가능하며 파일당 10MB, 최대 3천만 화소를 지원합니다. 휴대폰 EXIF 촬영 방향(회전·좌우 반전 포함)을 픽셀에 적용한 뒤 등록용 PNG로 저장합니다. 긴 변이 3000px보다 크면 축소합니다.
3. 새 내역은 **검토 대기**입니다. 사진 옆의 날짜·거래처·계정과목·적요·총금액·비고를 확인합니다. 문자 인식 원문과 분석 방식도 볼 수 있습니다.
4. 날짜·거래처·계정과목·적요·총금액을 입력하고 **확정하여 장부에 반영**을 누릅니다. 공급가액·부가세는 영수증에서 확인할 수 있을 때만 입력합니다. 총금액과 두 세액이 모두 있으면 합계 일치를 검사합니다.
5. 월·계정과목·검색어·상태로 조회하고 날짜·금액·계정과목순으로 정렬합니다. 검색에는 비고·사용자·부서도 포함됩니다.
6. **엑셀 내보내기**는 현재 월·계정과목·검색·정렬을 적용한 **확정 건만** 출력합니다. 상태 필터와 무관하게 확정 건을 출력합니다. 검토 대기 내역은 합계와 내보내기에서 제외됩니다.

같은 파일은 SHA-256으로 중복 등록을 방지합니다. 다시 촬영하거나 편집한 이미지는 다른 파일로 판단하므로 사람이 확인해야 합니다. 여러 장 등록은 차례로 처리합니다. 사진 없는 내역은 **직접 입력**을 사용하세요. 입력 후 저장하지 않고 닫아도 빈 검토 대기 내역은 남으며 삭제할 수 있습니다.

### 사진 방향 수정과 다시 읽기

새로 올리는 사진은 촬영 방향 정보를 자동으로 적용합니다. 이전 버전에서 이미 가로로 저장되었거나 촬영 방향 정보가 없는 사진은 검토 화면의 **왼쪽 90° / 오른쪽 90°** 버튼으로 바로 세우세요. 회전은 사진에 저장되며 입력 중인 내용은 화면에 유지됩니다.

그다음 **사진 다시 읽기**를 누르면 날짜·거래처·계정과목·금액·결제수단을 다시 추출하고 **검토 대기**로 바꿉니다. 적요·비고·사용자·부서는 유지합니다. 재인식 결과가 비어 있으면 기존 입력을 지우지 않고 오류를 표시합니다. 여러 창에서 동시에 수정하면 버전 충돌을 알리고 중단합니다. 이미 확정했던 내역도 재인식 후 다시 확인·확정해야 합니다.

같은 사진을 다시 업로드하면 새로 분석하는 대신 기존 항목이 열립니다. 이전 등록 사진을 고칠 때는 위의 회전·다시 읽기를 사용하세요. 식사 관련 분류는 제안이며 직원 식사인지 거래처 식사인지는 업무 목적에 따라 수정해야 합니다. 기본 OCR가 세액 표기를 읽지 못하면 해당 값은 빈칸으로 유지합니다.

시험용 영수증 `samples/sample-receipt.png`를 제공합니다. 실제 거래가 아닌 합성 예시입니다. 업로드 후 날짜 `2026-10-19`, 총금액 `22,000원` 등을 원본과 비교해 보세요. OCR 결과는 사진과 설치 언어에 따라 달라집니다. 자동 분류가 미분류이면 직접 선택하세요.

## 무료 기본 모드와 선택적 로컬 AI

### 기본 모드: Windows OCR + 규칙 분류

기본값이며 **생성형 AI가 아닙니다.** Windows 내장 OCR로 글자를 추출하고 명시된 합계·날짜·공급가액·부가세를 찾습니다. 식사·교통·사무용품 등의 키워드로 계정과목을 제안합니다. 업무 목적도 함께 참고합니다. 확인되지 않는 금액과 날짜는 빈칸으로 남깁니다. 세액을 총액의 10% 등으로 추정하지 않습니다.

Windows 10/11 및 설치된 OCR 언어 팩이 필요합니다. 인식 불가 메시지가 나오면 **Windows 설정 → 시간 및 언어 → 언어 및 지역 → 한국어 언어 옵션**에서 OCR 기능을 확인하세요. Windows 버전에 따라 메뉴 이름이 다릅니다. 관리자 PowerShell에서 설치 여부를 조회할 수도 있습니다.

```powershell
Get-WindowsCapability -Online | Where-Object Name -like 'Language.OCR*'
```

한국어 OCR 팩이 없으면 설정에서 설치하세요. 앱은 시스템 언어 설정을 자동으로 바꾸지 않습니다. OCR를 쓸 수 없어도 사진 검토와 직접 입력은 동작합니다. 숫자는 인식하더라도 업무 목적이나 계정과목은 정확하지 않을 수 있습니다. 사진은 똑바로 세우고 영수증 부분만 잘라서 올리는 편이 좋습니다. HEIC·PDF는 지원하지 않으며 JPG/PNG로 변환해야 합니다.

### 로컬 AI: Ollama + 이미지 모델 (선택)

API 사용료 없이 **이 PC에서 모델을 실행**합니다. 모델 설치를 사용자가 선택하도록 했으며 대용량 모델을 자동으로 설치하지 않습니다.

1. [Ollama 공식 사이트](https://ollama.com/download/windows)에서 Windows용 Ollama를 설치하고 실행합니다.
2. 터미널에서 `ollama pull gemma3:4b`를 실행합니다. 이미지 입력을 지원하는 4b 모델을 사용하세요. 최초 다운로드에는 수 GB의 공간과 인터넷이 필요합니다. 실제 메모리와 속도는 하드웨어·모델에 따라 달라집니다.
3. `application-local.properties.example`을 `application-local.properties`로 복사합니다.
4. `app.ollama-enabled=true`로 변경합니다. Ollama는 `http://127.0.0.1:11434`에서 실행되어 있어야 합니다.
5. 앱을 재시작하고 새 사진을 등록합니다. 화면의 분석 방식이 **로컬 AI 분석**인지 확인합니다.

AI는 이미지에서 구조화된 값을 추출하고 분류·비고를 제안합니다. 사진 내용은 로컬 Ollama에만 보내며 외부 유료 API를 호출하지 않습니다. 사진당 AI 요청 제한 시간은 150초입니다. 연결 또는 분석 실패 시 OCR·규칙 모드로 전환하고 이유를 표시합니다. 기존 등록 결과는 설정 변경만으로 재분석되지 않습니다. 필요하면 해당 내역을 직접 수정하거나 삭제 후 재등록하세요.

모델 설치·실행 및 AI 정확도는 별도로 확인해야 합니다. 자동 테스트에서는 가짜 로컬 Ollama HTTP 응답으로 요청 구조와 응답 파싱을 검증합니다. 실제 모델의 성능 검증을 대신하지 않습니다.

## 기장 기능

영수증을 확정한 후 검토 창의 **전표 기장**에서 기장일·대변 상대계정·담당자·부가세 처리 방식을 확인해 기장합니다. 기장 전표는 별도 분개장에서 조회·엑셀 출력하며, 취소 사유와 기장 당시 증빙도 보존합니다. 기존 확정 내역을 자동으로 기장하지 않습니다.

기장이 무엇인지, 차변·대변 예시, 취소·재기장 방법과 지원 범위는 [기장 기능 안내](docs/BOOKKEEPING.md)를 참고하세요. 이 기능은 영수증 지출의 기장 보조이며 전체 회계·결산·세무 신고를 처리하지 않습니다.

## 승인번호

영수증의 승인번호를 선택 항목으로 인식하고 검토 화면에서 수정할 수 있습니다. 앞자리 0을 문자열로 보존하며, 없는 경우에도 확정·기장할 수 있습니다. 기존 엑셀·구글 장부의 마지막 열과 기장 전표 사본에 함께 저장합니다. 기존 영수증은 자동 갱신되지 않으므로 검토 창의 **사진 다시 읽기** 또는 직접 입력을 사용하세요. [지원 표기와 사용 방법](docs/APPROVAL_NUMBER.md)

## 장부 양식 선택 근거

### 일반 영수증의 상호·지점·합계 인식

상단 상호와 별도 줄의 지점명을 함께 확인합니다. `수서점`처럼 지점명에 들어 있는 `서점`만으로 도서 구매라고 판단하지 않으며, 도서명·ISBN·문고 등 근거와 실제 품목을 참고합니다. 햄버거·정식 등 음식은 복리후생비, 수세미·종이접시 등은 소모품비로 제안합니다. 거래처 식사·회의 등 업무 목적을 입력했다면 해당 목적도 분류에 반영합니다.

`합계: 61,000`, `합 계 :: 61,000`, 금액이 다음 줄에 있는 합계, `결제대상금액`, `카드매출`, `카드결제(IC) 일시불 / 금액`을 지원합니다. 카드번호·승인번호·수량·포인트·깨진 소수점 숫자를 총액으로 가져오지 않습니다. 큰 글씨가 빠진 경우, OCR에서 위치를 확인한 합계·결제 행의 오른쪽 숫자 영역을 따로 읽고 유일한 금액일 때만 보완합니다. 인접한 금액이 여러 개면 임의로 선택하지 않습니다. 원본 사진은 유지하며 축소·명암·문자 두께를 달리한 분석 사본도 비교합니다.

업데이트 후에는 IntelliJ에서 실행 중인 앱을 종료하고 다시 실행하세요. 기존 내역은 검토 창의 **사진 다시 읽기**로 갱신합니다. 이전 지점명 오분류로 생성된 `도서 구입` 기본값은 분류 힌트로 재사용하지 않고, 도서가 아닌 것으로 재분석되면 해당 기본 적요·비고만 비웁니다. 직접 작성한 다른 적요·비고·사용자·부서는 보존합니다. 서체나 화질 때문에 상호의 일부 글자는 여전히 잘못 읽힐 수 있으므로 확정 전에 원본과 대조하세요.

### 도서 구매와 거래처 보정

영수증에 따라 원본 OCR와 영수증 영역 자르기·명암 보정·작은 점 인쇄 연결·180도 회전한 분석용 사본의 OCR를 비교합니다. 등록된 증빙 사진은 이 전처리로 변경하지 않습니다. 총금액은 카드 결제·결제 금액·승인 금액을 우선하고, `합계 2 43,700`의 권수와 금액을 구분합니다. 정가·할인액·면세/과세 소계·적립 포인트는 총액으로 선택하지 않습니다. 흐린 결제 표기의 숫자 일부는 인접한 권수·합계 행이 뒷받침할 때만 사용합니다. 총액 표기가 사라진 도서 영수증은 요약 영역에서 유일하게 반복되는 금액을 제안하고 화면에 근거를 표시합니다. 서로 다른 최종 결제 금액이 있거나 근거가 부족하면 총액을 빈칸으로 둡니다.

도서 구매는 `도서인쇄비`, 빈 적요/비고는 `도서 구입`으로 제안합니다. 사용자가 이미 입력한 적요·비고는 다시 읽기에서 보존합니다. 부가세를 읽지 못한 경우 책이라는 이유만으로 0원으로 채우거나 임의 계산하지 않습니다.

`data/merchant-rules.json`은 `{"사업자번호10자리":"확정된 상호"}` 형태의 PC 내부 거래처 보정 사전입니다. 상호를 수정하고 **확정**하면 OCR에서 확실하게 읽힌 단일 사업자번호에 그 상호를 기억합니다. 다음 영수증에서 같은 번호가 정확히 일치할 때만 사용하며, 파일명이나 비슷한 이름만으로 거래처를 강제하지 않습니다. 여러 사업자번호가 함께 있으면 자동 학습하지 않습니다. 현재 PC에는 제공된 영수증과 사용자 설명으로 확인한 미금문고를 이 사전에 등록했습니다. 이 사용자 데이터는 Git에서 제외됩니다. 백업할 때 `data` 폴더에 함께 포함하세요.

공식적으로 하나로 정해진 ‘경리 엑셀 표준’이 제공된 것은 아니므로 **일반 경비 지출내역서** 형태로 재구성했습니다. 특정 유료 서식을 복제하지 않았습니다.

- [Microsoft 경비 보고서 템플릿](https://excel.cloud.microsoft/create/en/expense-report-templates/): 날짜·금액·분류·증빙을 기록하고 합산하는 구조를 참고했습니다.
- [지출결의서 예시](https://formdown.kr/docs/doc-18/): 거래처·계정과목·적요·금액 구성을 참고했습니다.

실제 양식은 **계정별집계 + 지출장부** 두 탭입니다. 날짜와 금액은 엑셀의 실제 날짜·숫자 값이며 필터, 고정 행/열, 계정과목·결제수단 목록, 합계 수식을 넣었습니다. `빈 장부 양식`은 200행 입력 범위를 제공합니다. 범위를 넘어 직접 추가하면 수식·필터 범위도 늘려야 합니다. 앱에서 내보내는 파일은 해당 데이터 행 수로 다시 생성됩니다.

| 필드 | 용도 |
|---|---|
| 관리ID / 지출일자 / 거래처 | 중복 구분과 증빙 대조 |
| 계정과목 | 복리후생비, 여비교통비, 소모품비, 도서인쇄비, 회의비, 접대비, 통신비, 기타경비, 미분류 |
| 적요 / 비고 | 직원 점심, 밥값, 인원, 업무 목적 등의 설명 |
| 총금액 / 공급가액 / 부가세 | KRW 원 단위, 알 수 없는 세액은 빈칸 |
| 결제수단 / 사용자 / 부서 | 사내 경비 정산 정보 |
| 검토상태 / 분석방식 / 원본파일명 | 추출·확정 과정 추적 |

여기서 계정과목은 사내 검토를 위한 제안이며 회사의 회계 처리 기준에 맞게 수정해야 합니다. 영수증만으로 복리후생·접대 등의 실제 목적을 확정할 수 없습니다.

## Google 스프레드시트로 사용

### 방법 A: 계정 설정 없이 파일 가져오기

1. 앱에서 엑셀 파일을 내려받습니다. 빈 양식도 사용할 수 있습니다.
2. Google 스프레드시트 → **파일 → 가져오기 → 업로드**에서 `.xlsx`를 선택합니다.
3. 새 스프레드시트 생성 또는 시트 삽입을 선택합니다.

이 방식은 결과를 옮길 때 직접 업로드합니다. 자동 동기화가 아닙니다. [Google 공식 가져오기 안내](https://support.google.com/docs/answer/9331167?hl=ko)를 참고하세요.

### 방법 B: 서비스 계정으로 직접 전송 (선택)

별도 서버를 구매할 필요는 없습니다. Google 계정, 인터넷과 사용 가능한 API 권한이 필요하며 Google의 API 할당량과 조직 정책이 적용됩니다. 이 프로젝트에는 사용자 계정 또는 키가 포함되어 있지 않습니다.

1. Google Cloud Console에서 프로젝트를 만들거나 선택한 뒤 **Google Sheets API**를 사용 설정합니다.
2. IAM 및 관리자 → 서비스 계정에서 계정을 만들고 JSON 키를 발급합니다. 프로젝트 소유자 등 넓은 역할은 필요하지 않습니다. 조직에서 키 생성을 금지한 경우 방법 A를 사용하세요.
3. Google 스프레드시트를 하나 만든 후 JSON의 `client_email` 주소를 **편집자**로 공유합니다.
4. 프로젝트의 `secrets` 폴더에 JSON 키를 `service-account.json`으로 보관합니다. Git에서 제외되는 폴더입니다.
5. `application-local.properties`에 문서 URL의 `/d/`와 `/edit` 사이 ID를 입력합니다.

```properties
app.sheets-id=YOUR_SPREADSHEET_ID
app.sheets-credentials=./secrets/service-account.json
```

6. 앱 재시작 후 **전체 확정 장부 전송**을 누릅니다. **검색 조건과 무관하게 전체 확정 건**을 전송합니다.

앱이 `영수증장부_APP` 탭을 만들고 현재 확정 장부의 스냅샷으로 갱신합니다. 재전송해도 중복 행을 추가하지 않습니다. 수정·삭제 후 재전송하면 현재 장부를 반영합니다. **전용 탭의 A:O 범위는 앱이 관리하므로 직접 수정하지 마세요.** 수식·보고서는 별도 탭에서 작성하세요. 이름이 같은 기존 탭이 있고 첫 셀이 `관리ID`가 아니면 덮어쓰지 않고 중단합니다. 여러 PC에서 같은 문서를 동시에 동기화하는 용도로 설계하지 않았습니다.

사진은 Google에 전송하지 않고 장부의 값만 보냅니다. 문자열은 `RAW`로 보내 수식으로 해석하지 않습니다. 이 전송 기능은 자격 증명이 없으면 외부 요청을 실행하지 않습니다. **실제 사용자 문서 전송은 별도의 키·공유 설정 후 확인해야 합니다.**

참고: [서비스 계정 인증](https://developers.google.com/identity/protocols/oauth2/service-account), [Sheets 값 갱신 API](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/update).

## 코드 구조

```text
src/main/java/kr/local/receipts/
  ReceiptApplication.java  # IntelliJ 실행 진입점
  ApiController.java       # 사진 등록·수정·조회·파일·전송 HTTP API
  ReceiptService.java      # 이미지 검증·중복 방지·확정 조건
  ReceiptAnalyzer.java     # OCR 결과 파싱·규칙 분류·선택적 Ollama
  ReceiptTextParser.java   # 권수·정가·포인트와 결제 총액 구분
  ReceiptOcrImages.java    # 분석용 영역·명암·문자 두께·뒤집힘 보정
  MerchantDirectory.java  # 사업자번호 기반 PC 내부 거래처 보정
  WindowsOcr.java          # Windows 내장 OCR 프로세스 호출
  LedgerRepository.java   # JDBC와 H2 로컬 DB
  ExcelExporter.java      # Apache POI 경리 양식과 합계 수식
  GoogleSheetsSync.java   # 서비스 계정 인증·전용 탭 스냅샷 전송
  LocalWebSecurity.java   # 로컬 호스트 및 변경 요청 출처 제한
src/main/resources/static/ # HTML·CSS·JavaScript 화면 (외부 CDN 없음)
src/main/resources/scripts/windows-ocr.ps1
src/test/java/             # 실제 HTTP·DB·XLSX·로컬 AI 프로토콜 테스트
```

기술: **Java 17, Spring Boot 4.0.8, Maven Wrapper 3.9.9, Spring MVC/JDBC, H2, Apache POI 5.5.1, Jackson 3**. 유료 API나 Node/프런트 빌드 도구 없이 실행합니다. [Spring Boot 4.0 공식 요구 사항](https://docs.spring.io/spring-boot/4.0/system-requirements.html), [Windows OCR 언어](https://learn.microsoft.com/en-us/uwp/api/windows.media.ocr.ocrengine.availablerecognizerlanguages), [Ollama API](https://docs.ollama.com/api/generate).

## 테스트와 실행 파일

```powershell
.\mvnw.cmd test
.\mvnw.cmd package
java -jar target\receipt-to-excel-0.1.0.jar
```

테스트는 임시 H2 DB와 임시 이미지 폴더를 사용합니다. 사용자 장부를 변경하지 않습니다. 확정 조건, 세액 합계, 수정 충돌, 필터, 내보내기 합계, 문자열 수식 방지, 잘못된 이미지, 중복 등록, 로컬 요청 제한과 Ollama 구조화 응답을 검증합니다.

GitHub Actions CI는 커밋을 푸시하거나 PR을 만들 때 GitHub의 Windows·Java 17 환경에서 전체 테스트와 JAR 빌드를 실행합니다. 결과는 저장소 **Actions → ReceiptToExcel CI**에서 확인합니다. 최초 등록·수동 실행·실패 확인 방법과 검증 범위는 [CI 사용 안내](docs/CI.md)를 참고하세요. 실제 Windows OCR 인식률 확인과 배포 EXE 생성·릴리스 공개는 별도 작업입니다.

Windows에서 JAR로 앱을 실행 중이면 파일 잠금 때문에 같은 JAR로 다시 패키징할 수 없습니다. `package` 전에 해당 앱을 종료하세요. IntelliJ에서 소스를 실행하는 방식은 JAR를 잠그지 않습니다.

## 이번 버전 범위와 다음 요구사항

현재 **PC 사진 등록 → OCR/선택적 AI → 검토·확정 → 분류/정렬 → XLSX 또는 Google Sheets** 흐름과 별도의 **경비 전표 기장 → 분개장·취소 이력 → 기장 XLSX**를 구현했습니다. 구글 폼 자동 수집은 양식·사진 저장 위치·권한이 없으므로 포함하지 않았습니다. 나중에 연결한다면 앱 실행 시 폼 응답 시트와 Drive 사진을 가져오는 방식으로 확장할 수 있습니다. PC가 꺼져 있는 동안의 분석은 진행되지 않습니다.
